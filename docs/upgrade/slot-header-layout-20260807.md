# SR1010 双槽头部离线对照

日期：2026-08-07  
输入：当前 128 MiB 全闪存只读转储，结合实机 `versionstates` 给出的两个 header 地址。

## 已定位字段

两个记录分别位于 `0x02460000` 和 `0x04d60000`。记录开头的已确认布局：

| 相对偏移 | 内容 | 当前值 |
|---:|---|---|
| `0x08` | `upgrade_key1`，小端 uint32 | `0x510` |
| `0x0c` | `upgrade_key2`，小端 uint32 | `1` |
| `0x10` | 固件版本字符串 | `V1.0.0.2B5.8000` |
| `0x6c` | 产品字符串 | `ZXSLC SR1010` |
| `0xa8` | 构建时间字符串 | `20260609145652` |

这些值与实机 procfs 独立吻合，证明 flash 偏移和字节序均正确。

## 两个槽是不是不同版本

槽起点到各自 JFFS 起点的 `0x6e0000` 字节完全一致，SHA-256 同为：

```text
14fafffa2c034d0aaa9812292e54729e2948293dc3dc329500ea7844901d14a5
```

所以 kernel/早期镜像部分是完全镜像，并非两个版本。差异从两槽各自 JFFS 起点开始，属于
运行时可变文件系统内容。

两个 header 的前 `0x510` 字节也只有两段不同：`0x1f2..0x1f4` 和 `0x1fc..0x200`。
继续按小端 uint32 对齐并重算后，这两段现已精确闭环：

| 偏移 | 字段 | current | backup |
|---:|---|---:|---:|
| `0x1e0` | low start | `0x00600000` | 相同 |
| `0x1e4` | low end | `0x02f00000` | 相同 |
| `0x1e8` | high start | `0x02f00000` | 相同 |
| `0x1ec` | high end | `0x05800000` | 相同 |
| `0x1f0` | 本记录对应槽基址 | `0x00600000` | `0x02f00000` |
| `0x1f4` | 版本记录数量/上限 | `4` | `4` |
| `0x1f8` | 头部状态/格式字段（待命名） | `1` | `1` |
| `0x1fc` | header CRC32 | `0x136013e9` | `0xfc3db386` |

`0x1fc` 的值精确等于标准 CRC-32（Python/zlib）覆盖 header 相对偏移 `0x000..0x1fb`
的结果。两槽 CRC 不同完全由 `0x1f0` 的槽基址不同导致。这意味着外层头 CRC 的覆盖范围和
算法已经恢复，不再是未知项。

更强的交叉验证：把 current 头的 `+0x1f0` 从 `0x00600000` 改为 `0x02f00000`，随后重算
`+0x1fc` CRC，得到的全部 `0x510` 字节与真实 backup 头逐字节完全一致。因此这里已经
形成可逆重建闭环。

## 第二个 CRC：槽前导区

头部 `+0x98` 保存的 `0xd57e6630` 也已实算命中：它是标准 CRC-32 覆盖“对应槽基址开始的
`0x180000` 字节”。该区间恰好从槽起点延伸到 `versionstates` 报告的 image 地址：

```text
current: 0x00600000..0x00780000
backup:  0x02f00000..0x03080000
CRC32:   0xd57e6630
```

两槽前导区完全相同，因此这一 CRC 也相同。工具现会同时输出 `header_crc_ok` 和
`boot_prefix_crc_ok`。`+0x94` 的 `0x314` 以及相邻字段仍待调用点命名，本报告不把它们
强行解释成长度。

## 可重复工具

```powershell
python sr1010/tools/slot-header-compare.py whole-flash.bin
```

工具只读取镜像，输出两个头的 key、版本、产品、构建时间和差异范围，不输出序列号。

单独提取出 `0x510` 字节头后，可以离线换槽并自动修复 CRC：

```powershell
python sr1010/tools/slot-header-rebase.py current-header.bin backup-header.bin `
  --slot-base 0x02f00000
```

工具先验证输入 CRC，只接受本机已确认的两个槽基址，输出到新文件，不会原地覆盖输入。

## 实际意义

- 当前备用槽包含与活动槽相同的基础固件，可作为回滚底座。
- 不能把整个 41 MiB 槽做逐字节镜像判断，因为两个 JFFS2 会自然产生大量差异。
- 后续重建头部时必须按目标槽设置 `slot_base`，再对前 `0x1fc` 字节重算 CRC32。
