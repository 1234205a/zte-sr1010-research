# SR1010 固件升级零签名长度分支精确复核

日期：2026-08-07  
对象：当前B2 `/kmodule/bin/cspd`；仅离线静态逆向，没有生成升级包、调用升级事件或写MTD。

## 精确结论

此前只能从字符串`signlen is 0, do not verfy sign!`推测存在跳过分支。本轮已把字符串
交叉引用到`VerifySign`的实际控制流：

```text
sign_len = sign_object->field_0x10
if (sign_len != 0)
    goto verify_signature

log("signlen is 0, do not verfy sign!")
return 0
```

在当前实现中返回值`0`代表成功。因此可以确认：**当传入VerifySign的签名长度为0时，
密码学签名验证阶段直接成功返回**，并非仅打印日志后报错。

## 非零签名路径

签名存在时，函数还会：

- 要求特定模式下签名长度为`0x100`（256字节）；
- 读取/构造公钥材料；
- 计算待验证数据摘要；
- 调用注册的签名验证实现；
- 失败时统一返回负值。

固件包含DSA/RSA兼容验证组件和`UpgradeVerifySignRegister`回调注册机制，实际算法由产品
配置及升级头类型决定。

## 为什么仍不能直接称为“任意无签名固件可刷”

`VerifySign`只是完整升级链的一层。文件在到达它之前或之后仍需通过：

1. 升级头和文件完整性/CRC；
2. 产品、板型及版本策略；
3. `upgrade_key1/upgrade_key2`；
4. 分段长度和镜像布局；
5. flashing阶段写入及回读校验。

所以准确表述是“零sign_len绕过密码学签名这一层”，不是“任意文件都能刷”。要判断是否
能构造完整兼容升级包，还需恢复升级头结构、CRC覆盖范围和两个upgrade key的当前值来源。

## 工程意义

这条路径比修改Plugin分区风险高得多，而且会触碰双槽/MTD。当前自有程序持久化仍应优先
使用Plugin/JFFS2；升级链研究保留为固件格式兼容和恢复能力分析，不进行实机刷写。
